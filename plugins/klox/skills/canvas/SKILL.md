# Klox Canvas

Klox (https://klox.ai) is a visual canvas for AI video creation. You work on it through the `klox` MCP tools; the user watches and adjusts the same canvas in the browser. This skill is the working method. The tools' own descriptions and the server instructions are the contract, and they win if the two ever disagree.

Skill version 1.4.29. The latest version is always at https://klox.ai/agent/skills/canvas/SKILL.md.

## Before you start

- Call `list_workflows`. If the `klox` tools are missing or not authorized, follow https://klox.ai/agent to connect, then continue.
- The user pasted a Klox link (`/canvas/<id>` or `/preview/<token>`): fetch it as Markdown (append `.md`) to get its `workflowId`, then call `get_workflow`. If it returns `workflow_not_found`, tell the user the canvas does not exist (for a preview link: that you cannot edit it, and they can still view it there) and continue from accessible evidence.
- Reading an existing canvas, including a pasted link or continuing earlier work: keep calling `get_workflow` with `cursor: next` until `next` is null. The overview abbreviates long text (`truncated` and length fields); an `oversized` entry requires a detail read. Read `Brief` and any node you will act on in full with `nodeIds`; for a large previs node add `shots`. Use each edge's `order` for input numbering, not its position in the paged response. A `workflow_revision_conflict` means restart the overview; comments and task states can change between pages without a graph revision, so recheck current evidence before acting. The canvas is the whole project state; another agent or the user may have changed it since.
- Read `openComments` in `get_workflow`. They are notes the user pinned to nodes on the canvas for you, usually the most precise feedback you will get ("this shot is too dark"). Handle them as part of the current request, or tell the user why you did not, and close each with `resolve_comment` and one sentence on what you did.
- Give the user the canvas `previewUrl` early so they can watch alongside you; it opens without signing in and has an Edit button for them. If it is null, give `url` instead.

## What text nodes hold

Text nodes hold what a person decided: the Brief, the script, the shot list's dramatic jobs, grouping decisions and edit intent. Put everything else where it belongs:

- Computed state (exports, readiness, prices, gate and check status, Screen maps, shot windows, selected takes): read its current value from `get_workflow` when needed.
- Review evidence, what you inspected, what remains unverified, a migration or copy mapping: report it to the user in your reply. Wherever these skills say to record or report evidence, they mean that reply. Use the reply for review evidence and keep canvas nodes focused on production decisions and media.
- Planned pictures (state references, any keyframe): create titled and prompted image nodes for the planned pictures.
- Actions the previs cannot model: `shots[].notes`.

State each fact once in its owning node and refer to that node elsewhere. Write current production decisions directly; read approval status from the canvas. Keep each node focused on the current decision by rewriting it in place. Keep each node readable in about a minute (roughly 3,000 characters); split longer plans by scene.

## Making a video from scratch

For an episodic drama (a series, a pilot, a microdrama, a story adapted into episodes), also follow the Klox drama skill: it sets the stages, their order and what each must deliver. For designing reusable characters, locations or props, also follow the Klox asset-design skill. This section still covers the tools.

1. **Settle the creative decisions that change the result**, and only those the user has not already given or delegated: what it promotes or tells, where it will be shown (which sets the aspect ratio, for example 9:16 for short-video platforms), total length, style or mood, language of any on-screen text or voice. Ask them together in one short message. Use Seedance 2.5 (`seedance-2.5`) as the default video model. Follow the user's model choice; choose another model when the required input route or capability calls for it, checking `get_capabilities`. Choose suitable resolution and technical defaults within the requested scope. If the user says "you decide", decide and state your assumptions.
2. **Create the canvas** with `create_workflow`. Every canvas belongs to a project, one piece of work: leave `projectId` out for a new piece, or pass the `projectId` of the existing one (find it with `list_projects`) when this canvas continues it, for example the next episode of a series, so it shares that project's assets. Then write a text node titled `Brief` holding the decisions and constraints. Update it whenever the user changes them.
3. **Plan scenes, then their outputs** with `apply_workflow_change`. For a film whose blocking, scale or camera matters, read [previs.md](references/previs.md) before building it:
   - a script/Brief and a shot list with dramatic jobs, sound sources and planned cuts;
   - one shared previs node per needed scene, with actors, landmarks, action tracks and observations named by Shot IDs;
   - visual review through the previs node's `reviewUrl`, freezing a baseline before repairs and comparing after saving; follow [previs.md](references/previs.md#inspect-frames-on-the-review-page) for frame selection and evidence limits;
   - a greybox timing review in edit order, before expensive final images; connect previs exports to a compose timeline and use continuous playback of the assembled cut where available. Static review frames plus a cut plan leave dynamic timing and the assembled edit unverified;
   - a generation grouping plan before creating video nodes: preserve edit Shot IDs, but let one video node serve several compatible shots. Follow [generation planning](#generation-planning) below. A clip takes its previs Shot, or its ordered list of Shots, on `video`, and the asset nodes of what it shows as the default generation route. A continuous shot that one generation cannot hold continues in a later video node that extends it ([Continuing a shot](#continuing-a-shot)). Make a keyframe only for a picture the previs and assets cannot carry (an exact hand contact, text that must read), say why, and connect it where `get_capabilities.referenceVideoRoutes[model].openingFrame` says (`firstFrame`; `image` with `purpose: "opening"`; `null`: none beside a video). Check voice and other reference combinations separately;
   - a compose node fed by the accepted video takes, with the cut list controlling actual order and ranges.

   Simple shots without previs take their assets and a prompt (and, where composition matters, a sketch with `purpose: "layout"`). Choose the `firstFrame` route from the complete input combination; that frame carries the subjects' appearance. Call `get_capabilities` for actual modes, model options, duration limits and connections and use those current values when planning. For drama, its skill owns staging and review decisions.

4. **Write prompts you would accept as a finished brief for a single frame.** Name the subject, start state, setting, framing, lighting and style. For clips, add action intent, expression and sound. Previs-backed clips follow the [white-model reference/rendering workflow](references/video-models.md#white-model-reference-and-rendering): the reference guides space, camera and key events while assets supply the finished appearance. Briefly reinforce story-critical spatial relationships, action causality and continuous states in the prompt; ordinary travel and staging follow previs. Let generation develop natural performance and fine timing; increase precision for the named detail in a critical close-up. Without previs, describe the required camera move in the prompt. Describe recurring characters, locations and objects once, as assets (below), and keep shot prompts about the shot: action, framing, expression, light. Name each asset in the prompt as `@[Character A](asset:<assetId>)` (the `assetId` from `get_assets`) so the model knows which reference images belong to that subject, and point at a connected image, video or audio input as `@[Name](image:1)`, `@[Name](video:1)` or `@[Name](audio:1)`, counting that node's inputs of the type in execution order (stored inputs first, then edges by `order`, with selected previs Shots in their chosen order): "@[Character A](asset:a1) turns to @[Character B](asset:a2), framed like @[Layout](image:1)". Without assets, use consistent, concrete subject descriptions in every shot. Include readable text when required by the output and review its accuracy. For video, follow the model's habits in [video-models.md](references/video-models.md) (timestamps, dialogue, reference routing and extensions).
   When writing or revising video prompts, use the [prompt writing principles](references/prompt-writing.md): separate subjects and place, bind every asset mention, group action and sound under timed shot headings, and leave transitions open unless the production requires a specific one.
5. **Agree on a budget before spending credits.** Show the plan: which nodes you will generate, and a credit ceiling for it. Generation spends the user's credits; only generate what the user asked for.
6. **Generate with `run_nodes`** for anything beyond a single node: pass the approved production nodes (for example the first clip of each continuous shot, then their extensions after review) and the agreed `maxCredits`. Run compose separately after selecting and reviewing the takes. The server runs them in dependency order, also generating upstream nodes that have no result yet (review source clips before submitting dependent extensions or compose), stays within `maxCredits`, and keeps going if your session ends. Poll `get_generation_batch`, waiting at least `retryAfterMs`; it reports each node's status and `spentCredits`. A batch that stops with `stopCode: credit_limit` cannot fit its next task. Read the actual `spentCredits` and any active `productionRun.remainingCredits`; the ceiling need not be exhausted. Continue only within existing authorization. In an autonomous production run, plan within its fixed budget and report unfinished work when the remaining authorized tasks exceed it. `stop_generation_batch` stops new nodes from starting. Use `run_node` (and `get_task`) for a single node.
7. **Review before moving on.** Watch each take (the output `url` is public) before extending it or cutting with it; an extension inherits every flaw of the clip it continues. Review the greybox timing plan first where used, then generated takes and their joins, and finally the cut. Submit compose after the generated clips have passed review. Tell the user what you are keeping and what you are redoing.
8. **Compose** runs once the selected clips have been reviewed. Write the cut list as the compose node's timeline (`updateNodes[].composeTimeline`): video tracks for picture with their accepted native sound, audio tracks for carried sound, continuity repairs and music (the same video file placed on an audio track). Connection order alone does not set source ranges or cross-cut sound. Composing costs no credits. A saved timeline pins exact files, even after upstream nodes produce newer takes: replace affected timeline clips explicitly, preserving unaffected edits. Give the user the `previewUrl` to watch the film.

## Generation planning

Plan generation units separately from edit shots. Group neighbouring shots when they share scene, light, character state and a continuous action or dialogue passage, and the edit can tolerate some cut-point drift. Start by considering 2–4 shots over 6–15 seconds; longer groups suit simple, coherent passages that are easy to inspect. These are planning defaults, not capability guarantees or quotas. Keep precise contact, critical prop/state changes, strict lip-sync beats or shots likely to need independent repairs separate when grouping raises the cost of failure. Choose for expected usable footage and total cost, including retries and sound repairs, as the production objectives.

Keep a generation grouping plan in a text node for the decisions only: group ID, served Shot IDs in order, requested duration and handles, model/input route, assigned sound items, the audio setting of every row and the split-on-failure plan. Write each group's planned local intervals on its video node as `shotWindows`, not in text; after generation the actual source ranges live in the compose timeline (clips that name their shot), set through `check_cuts`, `confirm_cut_shot` and `replace_cut_shot`. Read export status, readiness, prices, gate and check results from `get_workflow` as current computed state. Target a first-pass footage ratio (initial requested video seconds / planned picture seconds) of about 1.3 or less; exceeding it triggers review and a recorded reason, not automatic rejection. Allow justified complete dialogue, sound tails and high-risk coverage. Report group count, this ratio, the actual generation ratio (requested video seconds across all attempts / final picture seconds), retake rate and credits in the production log. Price each group from its node's `readiness.credits` (the overview's `estimate` totals the canvas; a null price needs resolution before it can enter the budget), adding expected retries and sound repairs; fewer seconds imply proportional savings only with otherwise equal per-second pricing. Request enough time for the complete performance and sound tails with modest trim room, choosing each duration within current model limits. For drama, use its [detailed grouping procedure](https://klox.ai/agent/skills/drama/references/clips.md#generation-groups-before-video-nodes).

For grouped previs inputs, follow [connecting Shots and numbering references](references/previs.md#connect-a-shot) for ordered selections, updates and missing-Shot recovery. Reference numbers span all video inputs to the node, including other connections; recheck the full prompt mapping whenever inputs change. Check input and output limits separately through `get_capabilities`; reference count, total reference duration and any reference-plus-output limit may cap a group before its output maximum does. Check one representative group for blended references or ignored cut boundaries before grouping a whole episode. A group has at most one opening picture; identify any later reference image by cut and time in the prompt.

Generate dialogue, performance sounds, action effects, ambience and spatial acoustics with the video model. Enable native audio for clips whose scene sound will be used, including reaction and establishing coverage. Describe the sound sources, foreground/background balance, distance, enclosure and changes with the camera. Assign each scripted line and key event one source take, and carry it across picture cuts in the edit. Post-production handles joins, level balance, continuity, music and repairs, using the accepted native tracks as its starting point. A deliberately picture-only clip can use `generateAudio: false` with a chosen sound source for its edit slot.

At the pre-generation handoff, compare each group's audio setting with its intended use: native scene sound, carried sound, or picture-only coverage. A node with assigned source dialogue or events needs audio enabled. For `unassigned_audio_on`, review whether the clip supplies ambience or spatial sound and record its intended use; use the sound plan's source IDs for scripted lines and key events. Choose model capabilities and an explicit edit treatment that support the plan.

## Continuing a shot

When one continuous shot — picture, action and time carrying straight on, whether or not the camera moves — is longer than one generation holds well, continue the later part through video extension:

- Connect the earlier video node (or a video file) to the later node's `video` input with `purpose: "extend"`. Klox tells the model to continue it from its last frame and sends the adaptive aspect ratio; the node's ratio does not apply. The previs Shot of the continuation may also be connected as its blocking reference, plus the same asset nodes. Use the source video itself as the continuation input.
- Use a model whose `get_capabilities` → `referenceVideoRoutes[model].extend` is set, and the same model for the whole chain. `outputIncludesSource: true` (Wan 3.0): the output repeats the earlier clip first, so `duration` is its length plus the new part (within the model's reference-plus-output limit), `shotWindows` start after it, the edit takes the part after it, and the repeated seconds are paid again. `false` (Seedance 2.5): `duration` is the new part.
- Put the join between two lines of dialogue. The prompt says only what happens next (action, lines, changes), continuing the earlier clip's emotion and camera. Use the [extension timing convention](references/video-models.md#timing-an-extension) for output-local sections, planned shot windows and the continuation reference.
- Run an extension only after reviewing the clip it continues. Review the join where the edit cuts: the earlier clip's end against the continuation's start (Seedance) or against the continuation at the earlier clip's length (Wan); picture, motion and sound must carry on. A jump fails the take.
- When the earlier clip gets a newer result, every clip down the chain goes out of date (`extendSource` on the node, with the reason): `run_node` refuses to extend an out-of-date clip and any film using one (`extend_source_outdated`) until you regenerate from the first out-of-date clip.

## Reviews, gates and shot replacement

Use `get_workflow` for computed `readiness`, `shotGates`, `outputGate`, `roughCutGate` and `awaitingUser`. Fix `blocking` issues before submitting; `gates` identify whose review is missing; `warnings` identify risks to assess. Resolve a null credit estimate before budgeting that task. `creditsEstimated: true` means the node's inputs do not exist yet (no upstream result or export), so the price comes from its model and options alone; models priced by input length stay null until the inputs exist. The overview's `estimate` counts these in `estimatedNodes`.

During an active production run, follow its `policy.gates` for `previsShot`, `keyframe`, `clip`, `roughCut` and `film`. At an `agent` gate, inspect the actual item, then call `accept_gate_item` with `workflowId`, `item`, the current gate `fingerprint`, `evidence` locating the frames/clip/report you inspected, and a short `note`. A previs item is `{stage: "previsShot", shot: {previsNodeId, shotId}}`; other stages use `{stage, nodeId}`. At a `user` gate, present the item for the user's approval and continue independent work. Agent acceptance records the current review; check results retain their own authority. User approvals lock content; preserve approved shots, results, rough cuts and source-interval confirmations. For a canvas outside an active run, perform the generation authorized in the conversation. Autonomous run setup and user-owned gates follow the user's explicit choices.

For a take serving previs shots:

1. Write planned local intervals with `updateNodes[].shotWindows`: `[{shot: {previsNodeId, shotId}, start, end}]`, in chronological, disjoint intervals. Use the full shot reference: `S01` alone is not unique across scenes. Keep planned intervals separate from source ranges actually observed in the result.
2. After generation, run `check_cuts` on the video node. It detects cut timing and candidates, not shot identity. Inspect the actual video and read `get_sound_checks` for cut and sound decisions; use the run's exception policy for undecided checks. Keep paid repairs attributed with `checkItem`.
3. Confirm the observed interval with `confirm_cut_shot`: pass `workflowId`, `nodeId`, `shot`, `fileKey` of the result you watched, `planFingerprint` from that node's `shotWindowsFingerprint`, `sourceIn`, `sourceOut`, `evidence` and `note`. Use the reviewed file and plan, not values silently replaced by a newer read. A stale error requires reviewing the current version. This records Agent evidence; it does not replace a required user approval or the clip's gate acceptance.
4. Read the compose node's detail for `cutUpdates` (the overview gives `cutUpdateCount`). Use `replace_cut_shot` with `workflowId`, `composeNodeId`, `clipId` and `sourceNodeId` after the required reviews. It keeps the slot's position and duration. For takes with shot windows, a valid confirmation must cover the entire source range used; a shorter confirmed interval requires another take or a separate edit to the slot. Replacements are recorded and can be reverted.
5. Inspect `audioClipsFromOldSource`: detached audio on audio tracks keeps its old file. Decide separately whether to preserve or update it. Review the revised rough cut and pass its gate before rendering where required.

Saved compose timelines pin exact files. Initial default timelines and explicit edits are also checked against the actual generated media before an Agent can render them during a run. Use `clip.shot` to label the shot and complete the normal identity, gate and check review. Maintain actual order, trims and sound on the compose timeline; keep text notes for edit intent and unresolved decisions.

## Sound checks and production runs

For drama, follow the drama skill's sound planning and repair decisions. On the canvas:

- Create scene sound plans as `soundPlan` nodes. For a check, add an `audio` node with model `klox-sound-check`, connect the inspected video or compose node to its `source` input, and set `soundPlanNodeId` to the intended plan. Without it only a canvas with exactly one sound plan resolves automatically. An episode with several scenes needs a film check for each plan; each may read the same film.
- Read the report through `get_task` and delivery decisions through `get_sound_checks`. Clip reports locate dialogue in source-file time; film reports refer to their rendered timeline. Film release checks the timeline being submitted, so a line present in a take but cut out of that timeline requires an edit repair, not another take. Text transcription is evidence of wording, not speaker identity, voice consistency or lip sync. Untagged music, event material/count, room tone and double plays can remain undecided. For an undecided property, follow its supported listening or exception route.
- An active `productionRun` supplies the user's budget and evidence policy; it does not enlarge the creative scope. Reuse that authorization and read the drama skill's [autonomous-run procedure](https://klox.ai/agent/skills/drama/SKILL.md#autonomous-runs) for production. Initial generation can use `run_nodes`; paid repairs of a check use `run_node` with `checkItem`, because batches have no per-check attribution. Reserve credits for analysis as well as generation.
- `outputApprovedByUser` pins the chosen result even after new tasks succeed. `soundPlanApproved` and approved timeline clips protect their content. Keep them intact; a conflicting change requires the user to remove the approval on the canvas. An ordinary selected result (`outputSelectedByUser`) is different: a newer successful task can supersede it.

## Asset references and task prompts

Klox tells the model who each connected asset is and what each of its images is for: a character's identity (face and build) or current look (outfit, hair, makeup), as a face close-up, a turnaround or a single view; a location; an object. Character and object references supply appearance; the shot description and layout supply pose, position, expression and framing. Location references supply the place and its layout. Each asset node's `state` follows your prompt and overrides the references; on a video it describes the first frame only. An asset node can also carry up to two state images (`stateReferences`) that show where its state is and which way it faces; Klox names them as the subject's current state, sends them right after its first appearance reference, and tells the model they set the condition's place and direction, not pose or framing (on a video, at the first frame only). Everything else about the shot is your prompt's job.

**Names must resolve to visible references.** A bare story name does not tell the model who a character is or what a place looks like. Refer to a connected character asset with `@[Name](asset:<assetId>)`; when appearance is carried by a connected image or first frame, identify the person through that visible input or a concrete visual description. Without such grounding, use a self-contained visual description. Use names as labels for subjects grounded in visible references or a self-contained storyboard description. Keep story ownership, relationships and history out of visual prompts unless they change something visible or audible in this output. Required dialogue or readable in-world text may contain names.

Before running any image or video node, check each item:

1. **One moment per image.** An image node shows a single moment: a state reference or a START keyframe its moment, an END frame (a separate node, made from the accepted START) its end. Its prompt and its asset-node states describe that moment only. Changes between moments go in the video prompt. On a storyboard grid, check each panel as its own image.
2. **Each fact in one place.** A visible condition that holds through several shots (wet hair, a bandaged palm, blood on a sleeve, a changed eye colour) goes in the asset node's `state`, and that state matches the moment the node shows (for a video, its first frame); when it does not, connect another asset node. A condition only this shot shows goes in the prompt. Keep each condition in its owning state or prompt field. When where the condition is matters (a wound's side, an arrow's angle, the sleeve a stain is on), give that asset node state images made with the asset-design skill: the state text then says what the condition is ("arrow wound, bleeding"), and the side and direction come from the images alone; keep the state text focused on the condition. Text wins when the two contradict, so a side left in the text overrides the image you made to fix it.
3. **What differs from the references.** Name in the prompt what this shot changes from the references: pose, expression, an open coat, a different time of day at the location.
4. **Blocking in 3D (previs).** Use one shared scene for shots whose positions, scale or camera need to agree. Follow [previs.md](references/previs.md) for timeline edits, Shot selection, computed Screen maps, export readiness and current tool limits. The selected Shot must describe this shot's scene moment and framing; give actors distinct colors and their asset ids, and Klox names each coloured stand-in for the model.
5. **What each direct input is for.** An image on the `image` input that only guides layout or tone gets that purpose on its connection (`purpose: "layout"` or `"tone"`; `updateNodes[].inputPurposes` for one already connected), and Klox gives the model its role: a layout guide supplies subject positions, facing, camera angle and framing; a tone reference supplies colour, light and texture; an opening picture (`"opening"`, video nodes and reference images only) requests the clip's starting picture when strict first-frame input cannot accompany reference media. It does not guarantee an exact first frame. Use at most one opening picture per clip; later multi-cut keyframes have no purpose and are mapped to times in the prompt. A video on the `video` input can instead be the earlier part of the same continuous shot (`"extend"`, see [Continuing a shot](#continuing-a-shot)). Let the generated purpose notes establish that image's role; add the shot-specific action and performance. A layout guide controls the whole frame, so it must already show this shot's framing: crop or edit a wider master to match the tighter shot before connecting it. Give a sketch's placeholders distinct colours or labels and say in the prompt which is which subject ("the red figure is Character A"). For any other directly connected image (an image to edit, a storyboard grid), say in the prompt what it sets and what it does not.
6. **Crop fits the action.** Frame the action the shot is about; frame the hands or object clearly for an insert.
7. **Every subject is represented.** Connect each recurring subject's asset node unless a strict `firstFrame` keyframe carries its appearance. A reviewed state image may already carry an included prop's accepted design: add the prop's own reference only when that image lacks the detail the shot needs, following asset-design's state-image rules.

Write only the results of these checks into prompts, not the checks themselves. Review each output against them too: the model can still ignore a correct prompt.

## Storyboard grids

When static boards are useful, you can explore composition and rhythm with storyboard grids. A previs-backed scene instead tests spatial action and cameras in greybox playback and its timing cut. For grids: one image node per batch of shots, each panel one shot, in edit order. When the grids pass and a shot still needs a keyframe, make its guide match that panel's framing: crop or extract the panel, inspect it, and upload it before connecting it as a layout reference. With previs, use the actual Shot's opening layout. Connect an inspected single panel as the layout guide for its corresponding shot. With GPT Image models (`gpt-image-*`):

- **Write story beats, not shot lists.** For each panel, say what happens in this moment, why, and what the characters feel, then the shot size and camera. A list of framings alone gives flat, disconnected frames.
- **Open every grid prompt with one shared block**: a short summary of the story, the cast and locations described once, and the style. Refer to characters by name in the panels. Connect the same asset nodes to every grid.
- **Fix the layout in words**: panel count, rows and columns, reading order and separators. Choose panel count and sheet ratio so each shot remains readable at its intended aspect ratio; split crowded sheets.
- **Put shot labels and dialogue on the sheet**: a caption strip under each panel, with the exact text in quotes and "rendered verbatim exactly as written". Keep storyboard text in those caption strips. Produce clean picture references and video, add captions and titles in the edit, and include in-world text where the script calls for it.
- **Fix a single panel by editing the sheet**: connect the grid to a new image node and ask it to redraw only panel N with the correction and preserve the other panels.

## Recurring characters, locations and objects

Anything that must look the same in more than one shot is an asset of the project the workflow belongs to: a character, a location or another object (kind `other`: a product, a prop, a vehicle). In an ad, the product is an asset of kind `other`. Keep three things apart:

- **Identity** — the enduring features: age, face, eyes, build. Shared by every look.
- **Look** — what one act or scene changes: outfit, hair, makeup, accessories (a location by day and by night).
- **State** — what is true only in some shots: soaked hair, a bandaged palm, a torn sleeve. It belongs to the asset node feeding those shots, not to the look.

1. Read `get_assets`. If the canvas sits in the wrong project (the user made it on its own but it is part of a larger piece), ask them, then `move_workflow_to_project`.
2. Create each asset with `save_asset`: `kind`, `name`, an `identity.description` and a first look with its own `description`. The descriptions guide making the references; a generation gets only the reference images, so an asset works in a shot once it has them.
3. Use the asset-design skill to select a design, establish an accepted anchor and derive the views needed by the production. Keep exploration and explanatory boards in `designBoards`; save only inspected, accepted production images as references. Character identity and each look use one 3-view sheet: full-body front, full-body back and frontal face close-up. Establish and review the identity sheet first, using the supplied reference as an actual image input. Generate each look sheet from that accepted identity sheet as an actual image input, preserving the same face, build and body proportions while applying only the specified outfit, hair, makeup and accessories. Use a horizontal 16:9 row on neutral medium-grey with consistent soft diffuse light. Save the identity sheet in `identity.references` and each derived look sheet in that look's `references`, main sheet first; each reference carries its file key and, for locations when relevant, camera metadata. For new or substantially redesigned locations, follow asset-design's required sequence: generate and confirm design boards, then generate and confirm a clean master-view anchor, then derive camera and lighting references from that accepted anchor as an actual image input. An approved greybox alone does not replace these image reviews. Existing accepted locations can be reused. Locations need readable geography and relevant light states; props need shape, scale and functional states. Save chosen outputs’ `fileKey` under `identity.references` or the corresponding look’s `references` in priority order. Accept identity references through asset-design review and keep candidates in their exploration role. For a character who speaks, the voice is a clip in `identity.voiceClips`: if the user has a recording of the voice, upload it and save it there. If they want a voice made instead, write the voice design on the asset with `save_asset` first, then call `design_voice` with just the `assetId` (tell them the credits first); the design stays on the asset for the next round. `identity.voiceDescription` is the voice alone, describe the character's vocal register, texture, pace and accent, for example: "a woman in her mid-twenties, warm mid-range voice with a slight rasp, unhurried, calm and observant, neutral American accent". `identity.voiceSampleLine` is taken from the script: one of the character's own lines from a real scene on the canvas (the Brief, the script node or a shot prompt), in the language the video's dialogue uses, said in their everyday tone. Join two or three nearby lines of theirs to reach 100 characters, and put the most telling one first. If there is no dialogue yet, write a line they would plausibly say in the story. Put the clips it returns on the canvas as file nodes titled "<name> voice A", "B", "C" next to the asset, and ask them to listen on the preview and select the accepted voice. Save only the one they pick, keeping any clips already there; a voice they did not pick is not saved.
4. Add asset nodes with `addAssetNodes` and connect them to the `asset` handles of the image or video nodes they supply. Follow the subject-representation check above: a reviewed state image can already supply an included prop, and a strict first-frame route carries its subjects in the keyframe. The server sends the first look reference, state images, the first identity reference, then remaining look and identity images in saved order, within the model’s reference limit. Use one asset node per look and state; when the state changes (a character's jacket becomes soaked), add a second node of the same look with that `state` for the later shots. A run fails with `asset_reference_missing` when a connected asset has no reference image the model can take: make its references first, or pick a model that takes reference images. Add state images with `stateReferences: [{ fileKey }]` on `addAssetNodes` or `updateNodes` (an empty list clears them), key fact first. A run fails with `asset_state_reference_missing` when none of a node's state images fits (no room left beside the other references, a model that takes no reference images, or one that refuses them beside a first frame): make room, drop an input or change the model. A task that got only some lists the rest in `omittedStateReferences`; check what was lost before accepting the result. A video node animated from a keyframe (`firstFrame`) takes none, so let that keyframe carry the subjects' appearance; when a speaking character's voice clip must reach the clip on a model that takes no references with a first frame, use the keyframe as an `image` reference with the asset nodes instead.
5. Changing an asset's name, kind, reference images or voice clips advances its version (descriptions do not); results made from the older version are marked outdated on the canvas. Tell the user which shots that affects before regenerating them.

## Changing an existing project

- Change only what was asked. Locate nodes by their titles in `get_workflow` and edit the existing canvas in place.
- Every `apply_workflow_change` is recorded and the user can undo it from the canvas. If you made a mistake, undo it with `revert_workflow_change` and the returned `changeId`. It refuses with `workflow_change_conflict` and the `nodeIds` the user has edited since; then make a new change on top of theirs.
- `outputSelectedByUser: true` means the user picked that node's current result among several on the canvas. A newer successful task can replace their pick unless it is approved. Preserve the choice unless the requested change or existing authorization covers replacing it; otherwise confirm first.
- To redo a shot: update its prompt or options with `updateNodes`, then `run_node` it with a new idempotency key. Downstream results stay unchanged until rerun. Review the new take, regenerate the clips that extend it (they are now out of date), then explicitly update any saved compose timeline to the inspected take before rendering; rerunning compose alone keeps its pinned files.
- Keep existing results stored and review them against changed settings. Relevant prompt, input, asset, previs or Shot changes require affected downstream results to be reviewed or rerun. Display-only changes preserve result freshness. Start regeneration explicitly within the authorized scope.
- If the user edits the canvas while you work, your next change fails with `workflow_revision_conflict`. Read the canvas again, see what they changed, and build on it.

## Using media from elsewhere

If you or the user already have an image, video or audio file: `prepare_upload`, PUT the file to the returned URL with exactly the returned headers, `complete_upload`. Then decide what the file is:

- **The result of a node** — a shot or image rendered with another tool or a local model, standing in for what an image, video or compose node would have generated: attach it with `import_node_output` (with a short `note` on where it came from). It becomes that node's current result and flows to compose and other downstream nodes like a generated one, so the storyboard stays intact. It costs no credits and is marked as imported. Rerunning the node later produces a newer result that takes over; the user can switch between versions on the canvas.
- **Source material** — a reference video, a portrait, a product photo: add it with `addFileNodes` in `apply_workflow_change` and connect it where it is needed, for example as a reference (`video`), or as the video a clip extends (`purpose: "extend"`).

## Working on media locally

The compose timeline handles trims, several audio tracks, volume, fades and sound carried over cuts. Frame extraction, preview assembly from accessible files and captions can be done locally with `ffmpeg`, then uploaded. Check `ffmpeg -version` first; if it is missing, ask the user before installing anything. Keep originals untouched and write outputs to a working folder.

- **Split a video into segments** a model accepts (for example at most 15 seconds for reference-video models; `get_capabilities` lists each model's limits). Re-encode to place the cut at the requested time:
  `ffmpeg -ss 00:00:30 -i input.mp4 -t 15 -c:v libx264 -crf 18 -preset veryfast -c:a aac -movflags +faststart seg-03.mp4`
  Prefer scene boundaries when selecting cuts; watch or sample frames to find them.
- **First or last frame of a clip**, for review or an image edit (to continue a clip, extend it instead):
  `ffmpeg -i seg-03.mp4 -frames:v 1 seg-03-first.png` and `ffmpeg -sseof -0.1 -i seg-03.mp4 -frames:v 1 seg-03-last.png`
- **Results back to local**, for review or further editing: every output in `get_task` and `get_workflow` has a public `url`; `curl -L -o shot-03.mp4 '<url>'`.

Upload each derived file as above and give it a clear title (`Segment 3 (00:30-00:45)`), so the user can follow the canvas.
