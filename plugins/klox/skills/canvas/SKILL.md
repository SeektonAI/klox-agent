# Klox Canvas

Klox (https://klox.ai) is a visual canvas for AI video creation. You work on it through the `klox` MCP tools; the user watches and adjusts the same canvas in the browser. This skill is the working method. The tools' own descriptions and the server instructions are the contract, and they win if the two ever disagree.

Skill version 1.4.15. The latest version is always at https://klox.ai/agent/skills/canvas/SKILL.md.

## Before you start

- Call `list_workflows`. If the `klox` tools are missing or not authorized, follow https://klox.ai/agent to connect, then continue.
- The user pasted a Klox link (`/canvas/<id>` or `/preview/<token>`): fetch it as Markdown (append `.md`) to get its `workflowId`, then call `get_workflow`. If it returns `workflow_not_found`, tell the user the canvas does not exist (for a preview link: that you cannot edit it, and they can still view it there); do not guess its contents.
- Continuing earlier work: call `get_workflow` on that canvas and read the node titled `Brief` first. The canvas is the whole project state; there is no chat history on the Klox side, and another agent or the user may have changed it since.
- Read `openComments` in `get_workflow`. They are notes the user pinned to nodes on the canvas for you, usually the most precise feedback you will get ("this shot is too dark"). Handle them as part of the current request, or tell the user why you did not, and close each with `resolve_comment` and one sentence on what you did.
- Give the user the canvas `previewUrl` early so they can watch alongside you; it opens without signing in and has an Edit button for them. If it is null, give `url` instead.

## Making a video from scratch

For an episodic drama (a series, a pilot, a microdrama, a story adapted into episodes), also follow the Klox drama skill: it sets the stages, their order and what each must deliver. For designing reusable characters, locations or props, also follow the Klox asset-design skill. This section still covers the tools.

1. **Settle the creative decisions that change the result**, and only those the user has not already given or delegated: what it promotes or tells, where it will be shown (which sets the aspect ratio, for example 9:16 for short-video platforms), total length, style or mood, language of any on-screen text or voice. Ask them together in one short message. Model choice, resolution and similar technical settings have sensible defaults; do not ask about them. If the user says "you decide", decide and state your assumptions.
2. **Create the canvas** with `create_workflow`. Every canvas belongs to a project, one piece of work: leave `projectId` out for a new piece, or pass the `projectId` of the existing one (find it with `list_projects`) when this canvas continues it, for example the next episode of a series, so it shares that project's assets. Then write a text node titled `Brief` holding the decisions and constraints. Update it whenever the user changes them.
3. **Plan scenes, then their outputs** with `apply_workflow_change`. For a film whose blocking, scale or camera matters, read [previs.md](references/previs.md) before building it:
   - a script/Brief and a shot list with dramatic jobs, sound sources and planned cuts;
   - one shared previs node per needed scene, with actors, landmarks, action tracks and observations named by Shot IDs;
   - a greybox timing review in edit order, before expensive final images; use available exports and local assembly, or explicitly report the limitation of browser playback plus a cut plan;
   - image nodes for the reviewed opening keyframes needed by the route, fed by the matching previs Shot's `image` output and project assets;
   - one video node per shot by default. A previs-backed clip takes its Shot on `video`; choose the opening picture input from `get_capabilities.referenceVideoRoutes`. `firstFrame` means that combination is legal, `image` means a normal image with `purpose: "opening"`, and `null` means no opening-picture input beside the video. Check voice and other reference combinations separately;
   - a compose node fed by the accepted video takes, with the cut list controlling actual order and ranges.

   Simple shots can use first-frame or reference-image generation without previs. Do not choose `firstFrame` just because the clip has no dialogue: legality depends on every input. A strict first frame can carry appearance; reference routes need the required asset inputs. Call `get_capabilities` for actual modes, model options, duration limits and connections; do not copy provider capability tables into the production plan. For drama, its skill owns staging and review decisions.

4. **Write prompts you would accept as a finished brief for a single frame.** Name the subject, start state, setting, framing, lighting and style. For clips, add action intent, expression and sound. A selected previs reference owns the motion and camera; do not write a conflicting camera path. Without previs, describe the required camera move in the prompt. Describe recurring characters, locations and objects once, as assets (below), and keep shot prompts about the shot: action, framing, expression, light. Name each asset in the prompt as `@[Character A](asset:<assetId>)` (the `assetId` from `get_assets`) so the model knows which reference images belong to that subject, and point at a connected image, video or audio input as `@[Name](image:1)`, `@[Name](video:1)` or `@[Name](audio:1)`, counting that node's inputs of the type: "@[Character A](asset:a1) turns to @[Character B](asset:a2), framed like @[Layout](image:1)". Without assets, repeat the same concrete descriptions in every shot instead of writing "the same person". Avoid asking for readable text inside images unless it matters; image and video models often garble it.
5. **Agree on a budget before spending credits.** Show the plan: which nodes you will generate, and a credit ceiling for it. Generation spends the user's credits; only generate what the user asked for.
6. **Generate with `run_nodes`** for anything beyond a single node: pass the approved production nodes (for example required keyframes, then their clips after review) and the agreed `maxCredits`. Run compose separately after selecting and reviewing the takes. The server runs them in dependency order, also generating upstream nodes that have no result yet (so never pass a clip or compose node while its keyframes are unreviewed), never spends more than `maxCredits`, and keeps going if your session ends. Poll `get_generation_batch`, waiting at least `retryAfterMs`; it reports each node's status and `spentCredits`. A batch that stopped with `stopCode: credit_limit` spent what it could; tell the user and ask before starting another. `stop_generation_batch` stops new nodes from starting. Use `run_node` (and `get_task`) for a single node.
7. **Review before moving on.** Look at each keyframe (the output `url` is public) and fix weak ones before animating them; a bad keyframe makes a bad clip. Review the greybox timing plan first where used, then required keyframes, then generated takes, and finally the cut. Do not batch compose together with unreviewed clip generation simply because all dependencies can run. Tell the user what you are keeping and what you are redoing.
8. **Compose** runs once the selected clips have been reviewed. Apply the cut list in the compose editor or supported local assembly; connection order alone does not establish correct source ranges or cross-cut sound. Composing costs no credits. Give the user the `previewUrl` to watch the film.

## Asset references and task prompts

Klox tells the model who each connected asset is and what each of its images is for: a character's identity (face and build) or current look (outfit, hair, makeup), as a face close-up, a turnaround or a single view; a location; an object. It also tells the model that character and object references never set pose, position, expression, framing or background, while a location reference sets the place and its layout. Each asset node's `state` follows your prompt and overrides the references; on a video it describes the first frame only. An asset node can also carry up to two state images (`stateReferences`) that show where its state is and which way it faces; Klox names them as the subject's current state, sends them right after its first appearance reference, and tells the model they set the condition's place and direction, not pose or framing (on a video, at the first frame only). Everything else about the shot is your prompt's job.

**Names must resolve to visible references.** A bare story name does not tell the model who a character is or what a place looks like. Refer to a connected character asset with `@[Name](asset:<assetId>)`; when appearance is carried by a connected image or first frame, identify the person through that visible input or a concrete visual description. Without such grounding, use a self-contained description rather than an unexplained name. Names may label subjects already defined in a self-contained storyboard brief, but never substitute for appearance references. Keep story ownership, relationships and history out of visual prompts unless they change something visible or audible in this output. Required dialogue or readable in-world text may contain names.

Before running any image or video node, check each item:

1. **One moment per image.** An image node shows a single moment: a START keyframe its shot's start, an END frame (a separate node, made from the accepted START) its end. Its prompt and its asset-node states describe that moment only. Changes between moments go in the video prompt. On a storyboard grid, check each panel as its own image.
2. **Each fact in one place.** A visible condition that holds through several shots (wet hair, a bandaged palm, blood on a sleeve, a changed eye colour) goes in the asset node's `state`, and that state matches the moment the node shows (for a video, its first frame); when it does not, connect another asset node. A condition only this shot shows goes in the prompt. Never write a fact in both. When where the condition is matters (a wound's side, an arrow's angle, the sleeve a stain is on), give that asset node state images made with the asset-design skill: the state text then says what the condition is ("arrow wound, bleeding"), and the side and direction come from the images alone; do not write left, right or a direction in the text. Text wins when the two contradict, so a side left in the text overrides the image you made to fix it.
3. **What differs from the references.** Name in the prompt what this shot changes from the references: pose, expression, an open coat, a different time of day at the location.
4. **Blocking in 3D (previs).** Use one shared scene for shots whose positions, scale or camera need to agree. Follow [previs.md](references/previs.md) for timeline edits, Shot selection, computed Screen maps, export readiness and current tool limits. The selected Shot must describe this shot's scene moment and framing; give actors distinct colors and map them to subjects in the prompt.
5. **What each direct input is for.** An image on the `image` input that only guides layout or tone gets that purpose on its connection (`purpose: "layout"` or `"tone"`; `updateNodes[].inputPurposes` for one already connected), and Klox tells the model what it may and may not decide: a layout guide sets where subjects stand, which way they face, the camera angle and framing, never appearance; a tone reference sets colour, light and texture, never content or framing; an opening picture (`"opening"`, video nodes and reference images only) requests the clip's starting picture when strict first-frame input cannot accompany reference media. It does not guarantee an exact first frame. Use at most one opening picture per clip; later multi-cut keyframes have no purpose and are mapped to times in the prompt. Do not explain a purposed image again in the prompt. A layout guide controls the whole frame, so it must already show this shot's framing: crop or edit a wider master into a guide for a tighter shot rather than connecting the wide one. Give a sketch's placeholders distinct colours or labels and say in the prompt which is which subject ("the red figure is Lena"). For any other directly connected image (an image to edit, a storyboard grid), say in the prompt what it sets and what it does not.
6. **Crop fits the action.** Frame the action the shot is about; an insert of hands or an object frames them, not a face.
7. **Every subject is connected.** Each recurring subject in frame has its asset node connected, or is already in the keyframe on a `firstFrame` route.

Write only the results of these checks into prompts, not the checks themselves. Review each output against them too: the model can still ignore a correct prompt.

## Storyboard grids

When static boards are useful, you can explore composition and rhythm with storyboard grids. A previs-backed scene instead tests spatial action and cameras in greybox playback and its timing cut. For grids: one image node per batch of shots, each panel one shot, in edit order. When the grids pass, make each keyframe's guide match that panel's framing: crop or extract the panel, inspect it, and upload it before connecting it as a layout reference. With previs, use the actual Shot's opening layout instead of a competing whole grid. Never connect a grid to a video node; every clip starts from its own keyframe. With GPT Image models (`gpt-image-*`):

- **Write story beats, not shot lists.** For each panel, say what happens in this moment, why, and what the characters feel, then the shot size and camera. A list of framings alone gives flat, disconnected frames.
- **Open every grid prompt with one shared block**: a short summary of the story, the cast and locations described once, and the style. Refer to characters by name in the panels. Connect the same asset nodes to every grid.
- **Fix the layout in words**: the number of panels, rows and columns, reading order, thin black borders and white gutters. Keep six to eight panels per image and split longer sequences into several grids. Pick the image ratio from the panel grid (3 columns × 2 rows of vertical 9:16 panels fits 3:4); avoid 16:9 for multi-row grids, which squeezes panels into strips.
- **Put shot labels and dialogue on the sheet**: a caption strip under each panel, with the exact text in quotes and "rendered verbatim exactly as written, no extra characters". Allow no other text. This applies to storyboards only; keyframes and video carry no captions, titles or overlaid text, and in-world text (a phone screen, a sign) appears only where the script needs it.
- **Fix a single panel by editing the sheet**: connect the grid to a new image node and ask it to redraw only panel N with the correction and keep every other panel unchanged, instead of regenerating the whole grid.

## Recurring characters, locations and objects

Anything that must look the same in more than one shot is an asset of the project the workflow belongs to: a character, a location or another object (kind `other`: a product, a prop, a vehicle). In an ad, the product is an asset of kind `other`. Keep three things apart:

- **Identity** — what never changes: age, face, eyes, build. Shared by every look.
- **Look** — what one act or scene changes: outfit, hair, makeup, accessories (a location by day and by night).
- **State** — what is true only in some shots: soaked hair, a bandaged palm, a torn sleeve. It belongs to the asset node feeding those shots, not to the look.

1. Read `get_assets`. If the canvas sits in the wrong project (the user made it on its own but it is part of a larger piece), ask them, then `move_workflow_to_project`.
2. Create each asset with `save_asset`: `kind`, `name`, an `identity.description` and a first look with its own `description`. The descriptions guide making the references; a generation gets only the reference images, so an asset works in a shot once it has them.
3. Use the asset-design skill to select a design, establish an accepted anchor and derive the views needed by the production. Keep exploration and explanatory boards in `designBoards`; save only inspected, accepted production images as references. A character usually needs a clean body anchor and a face close-up for dialogue; turnarounds and detail views follow actual use, not a mandatory six-view template. For new or substantially redesigned locations, follow asset-design's required sequence: generate and confirm design boards, then generate and confirm a clean master-view anchor, then derive camera and lighting references from that accepted anchor as an actual image input. An approved greybox alone does not replace these image reviews. Existing accepted locations can be reused. Locations need readable geography and relevant light states; props need shape, scale and functional states. Save chosen outputs' `fileKey` with the existing view tags (`turnaround` for a multi-view sheet, `face` for a face close-up, `other` for single views, locations or objects): identity references under `identity.references`, look-specific references under the look's `references`. Never promote an unreviewed story shot or comparison board to an identity reference. For a character who speaks, the voice is a clip in `identity.voiceClips`: if the user has a recording of the voice, upload it and save it there. If they want a voice made instead, write the voice design on the asset with `save_asset` first, then call `design_voice` with just the `assetId` (tell them the credits first); the design stays on the asset for the next round. `identity.voiceDescription` is the voice alone, rebuilt from the character rather than copied from `identity.description`: "a woman in her mid-twenties, warm mid-range voice with a slight rasp, unhurried, calm and observant, neutral American accent". `identity.voiceSampleLine` is taken from the script: one of the character's own lines from a real scene on the canvas (the Brief, the script node or a shot prompt), in the language the video's dialogue uses, said in their everyday tone rather than at their loudest or most upset moment. Join two or three nearby lines of theirs to reach 100 characters, and put the most telling one first. If there is no dialogue yet, write a line they would plausibly say in the story. Put the clips it returns on the canvas as file nodes titled "<name> voice A", "B", "C" next to the asset, and ask them to listen on the preview and pick one: you cannot hear the clips. Save only the one they pick, keeping any clips already there; a voice they did not pick is not saved.
4. Add asset nodes with `addAssetNodes` and connect each to the `asset` handle of every image or video node that shows it. The server sends each asset's turnaround sheets (if any) first, then face close-ups (if any), then its remaining references, within the model's reference limit. A front anchor tagged `other` is among those remaining references. Use one asset node per look and state; when the state changes (a character's jacket becomes soaked), add a second node of the same look with that `state` for the later shots. A run fails with `asset_reference_missing` when a connected asset has no reference image the model can take: make its references first, or pick a model that takes reference images. Add state images with `stateReferences: [{ fileKey }]` on `addAssetNodes` or `updateNodes` (an empty list clears them), key fact first. A run fails with `asset_state_reference_missing` when none of a node's state images fits (no room left beside the other references, a model that takes no reference images, or one that refuses them beside a first frame): make room, drop an input or change the model. A task that got only some lists the rest in `omittedStateReferences`; check what was lost before accepting the result. A video node animated from a keyframe (`firstFrame`) takes none, so let the keyframe carry the subjects and connect no asset nodes to it; when a speaking character's voice clip must reach the clip on a model that takes no references with a first frame, use the keyframe as an `image` reference with the asset nodes instead.
5. Changing an asset's name, kind, reference images or voice clips advances its version (descriptions do not); results made from the older version are marked outdated on the canvas. Tell the user which shots that affects before regenerating them.

## Changing an existing project

- Change only what was asked. Locate nodes by their titles in `get_workflow`; never recreate a canvas the user has been editing.
- Every `apply_workflow_change` is recorded and the user can undo it from the canvas. If you made a mistake, undo it with `revert_workflow_change` and the `changeId` it returned instead of writing the inverse by hand. It refuses with `workflow_change_conflict` and the `nodeIds` the user has edited since; then make a new change on top of theirs.
- `outputSelectedByUser: true` means the user picked that node's current result among several on the canvas. Regenerating the node replaces their pick, so confirm first.
- To redo a shot: update its prompt or options with `updateNodes`, then `run_node` it with a new idempotency key. Downstream nodes keep using their old inputs until they run again, so rerun the clip that uses a new keyframe, then compose.
- Existing results remain stored when settings change; that does not prove they match the new plan. Relevant prompt, input, asset, previs or Shot changes require affected downstream results to be reviewed or rerun. Display-only changes do not. Nothing regenerates automatically.
- If the user edits the canvas while you work, your next change fails with `workflow_revision_conflict`. Read the canvas again, see what they changed, and build on it.

## Using media from elsewhere

If you or the user already have an image, video or audio file: `prepare_upload`, PUT the file to the returned URL with exactly the returned headers, `complete_upload`. Then decide what the file is:

- **The result of a node** — a shot or keyframe rendered with another tool or a local model, standing in for what an image, video or compose node would have generated: attach it with `import_node_output` (with a short `note` on where it came from). It becomes that node's current result and flows to compose and other downstream nodes like a generated one, so the storyboard stays intact. It costs no credits and is marked as imported. Rerunning the node later produces a newer result that takes over; the user can switch between versions on the canvas.
- **Source material** — a reference video, a portrait, a product photo: add it with `addFileNodes` in `apply_workflow_change` and connect it where it is needed, for example as a keyframe (`firstFrame`) or a reference (`video`).

## Working on media locally

Use the compose editor for its supported trims. Frame extraction, preview assembly from accessible files, captions and mixing can be done locally with `ffmpeg`, then uploaded. Check `ffmpeg -version` first; if it is missing, ask the user before installing anything. Keep originals untouched and write outputs to a working folder.

- **Split a video into segments** a model accepts (for example at most 15 seconds for reference-video models; `get_capabilities` lists each model's limits). Re-encode so the cut lands exactly where you asked instead of on the nearest keyframe:
  `ffmpeg -ss 00:00:30 -i input.mp4 -t 15 -c:v libx264 -crf 18 -preset veryfast -c:a aac -movflags +faststart seg-03.mp4`
  Cut at scene changes where you can rather than at fixed intervals; watch or sample frames to find them.
- **First or last frame of a clip**, for an image-edit keyframe or to continue from where a clip ends:
  `ffmpeg -i seg-03.mp4 -frames:v 1 seg-03-first.png` and `ffmpeg -sseof -0.1 -i seg-03.mp4 -frames:v 1 seg-03-last.png`
- **Results back to local**, for review or further editing: every output in `get_task` and `get_workflow` has a public `url`; `curl -L -o shot-03.mp4 '<url>'`.

Upload each derived file as above and give it a clear title (`Segment 3 (00:30-00:45)`), so the user can follow the canvas.

## Errors

| Code                         | What to do                                                                                                                                                                                                                         |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `workflow_revision_conflict` | Call `get_workflow` again, reconcile with what changed, resubmit against the new revision.                                                                                                                                         |
| `workflow_change_rejected`   | Nothing was applied. Fix the operations listed in `rejections` (index and reason) and resubmit the whole change.                                                                                                                   |
| `previs_render_required`     | The selected Shot lacks a current export. Have the owner open the editor, let connected exports complete, re-read `get_workflow`, then retry the same uncreated request. Do not blindly poll or infer readiness from elapsed time. |
| `upstream_output_missing`    | Run the listed upstream nodes first.                                                                                                                                                                                               |
| `node_task_in_progress`      | That node is already generating; wait for its task.                                                                                                                                                                                |
| `insufficient_credits`       | Stop generating and tell the user they need more credits at https://klox.ai/pricing.                                                                                                                                               |
| `workflow_change_conflict`   | The user edited the listed nodes after your change, so it cannot be undone automatically. Make a new change instead.                                                                                                               |
| `email_not_verified`         | Ask the user to confirm their email from the message Klox sent them, then retry.                                                                                                                                                   |
| `insufficient_scope`         | The user did not allow generation for this connection. Ask whether they want to reconnect and allow it.                                                                                                                            |
| A task ends `failed`         | Report the `errorCode`. Retry once, with a new idempotency key, only if adjusting the prompt or settings is likely to help; do not loop.                                                                                           |

Reuse the same idempotency key only when retrying the very same request after a timeout or lost response. That is what keeps a retry from charging twice.
